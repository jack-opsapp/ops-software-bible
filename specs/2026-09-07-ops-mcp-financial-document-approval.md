# Phase 15 — private estimate and change-order drafts

Status: implemented and verified locally on 2026-09-07. Production migration and release pending. Financial exposure, consent, company policy enrollment and real-document acceptance remain unapproved and inactive.

## Contract

The host-neutral capability service adds `inspect_financial_document` and `prepare_financial_document`. MCP provides typed discovery/transport only. The existing OPS approval desk owns exact named-operator confirmation; `commit_financial_document` is not an external MCP tool. The active v20 manifest / v14 exposure / v9 consent are unchanged. v23 manifest and v17 exposure are implementation candidates, absent from selectable exposure. Consent v12 is not installed. Earlier dormant definitions remain intact.

Inspection returns the exact live client/target, versioned financial policy and requested bounded source identities/hashes. Preparation supports a new estimate, an additional-scope change-order draft against an approved/converted estimate on the exact project, or a new immutable revision of a draft/changes-requested predecessor. `parent_id` identifies the preceding revision; `baseline_estimate_id` separately identifies the accepted baseline. Change-order totals are proposed additional scope, never an updated contract total or recorded acceptance. Prior documents and lines are preserved byte-for-byte.

Each proposal seals company, actor, OAuth client/grant, current permission snapshot, source versions, pricing policy, proposed document, expected effects and an expiry 30 minutes away. Preparation creates only an internal proposal, run/action and persistent review notification. It does not reserve a number or create a financial document. OPS approval submits the exact proposal hash/change-set identity using a deterministic action-specific key. Approval edits require a new preparation; bulk, autonomous and generic approval shortcuts reject this action type.

## Authority and pricing

Required all-scope permissions: `agent.review`, `clients.view`, `estimates.create`, `estimates.view`, `pipeline.view`, `projects.view`. Required scopes: `ops.company.read`, `ops.customers.read`, `ops.financial_documents.prepare`, `ops.financial_documents.read`, `ops.jobs.read`. The canonical actor resolver rechecks current permissions. Commit and receipt replay recheck the original current grant/client and registered revisions. Browser action RLS also checks every required business permission; the service queue filter rechecks OAuth authority. Deleted or merged source clients/projects are unavailable.

`private.financial_document_policies` holds exact company/revision/status, CAD or USD currency, terms, permitted price-source kinds and permitted units, with an attributable versioned project-note source/hash. No business policy or Canpro rule is seeded. Missing/conflicting policy blocks inspection/preparation. Canpro's conflicting sources must be reconciled and a specific authoritative policy enrolled under separate business authority before any real financial proposal can succeed.

Supported price sources are basic active catalogue products, exact lines from approved/converted estimates on completed jobs, or explicitly attributed operator prices when the policy permits them. Catalogue tier/bundle/configured ambiguity is refused. Source currency must match; legacy historical/baseline currency-null documents block rather than assuming today's company currency. Unsupported units, source relationships, stale hashes, ambiguous taxes, hidden fields and malformed JSON fail closed. Source notes remain untrusted business data, rendered as inert text.

All arithmetic runs in PostgreSQL numeric. Quantities allow three decimal places, monetary prices two, discounts/increase two. An 8% increase applies only to unit prices and minimum charges, then rounds them to cents. Quantity and discount values remain explicitly shown. The existing generated line-total convention applies the discount before the minimum floor. Tax is rounded once over the taxable subtotal; incremental per-line allocations sum exactly to that amount. One active default tax rate is required. CAD/USD, nonnegative totals below numeric(12,2)'s ceiling, 1–100 lines, explicit issue/expiry civil dates, and an authoritative units list are bounded supported inputs. Issue dates must be within one day of current UTC; expiry is no earlier than issue and no later than 366 days after issue. New proposals contain no optional/configured/hierarchical line behavior, document-level discount or deposit; those fields cannot be silently supplied. The full previous revision remains in revision previews.

All hash-producing source functions run with UTC session configuration so timestamp serialization cannot change across pooled connections. Requested source metadata and referenced catalogue/history dependency rows participate in staleness checks.

## Atomic save and delivery custody

`persist_private_financial_document` is a private server-only primitive. It revalidates sources, serializes initial sequence creation and increments, creates the header and every line, then compares the persisted header/lines against the exact approved content. Number padding never truncates a six-digit sequence. Canonical rows and their full digest form the receipt. Proposal/action completion, notification resolution and receipt persistence share the transaction. The approval service independently reloads the action and compares the complete receipt, ignoring only the replay flag. Ambiguous response reconciliation uses the same deterministic key; no new financial identity is invented.

New estimate metadata: `distribution_hold`, `document_kind`, `baseline_estimate_id`, `currency_code`, `scope_inclusions`, `scope_exclusions`. Every saved draft has `distribution_hold=true`, draft status, and no customer/provider state. Guard triggers forbid updates/deletion of held revisions and insertion/replacement/deletion of their lines outside the exact private transaction token. Corrections require a newly approved revision. No release, send, accept, invoice, payment or refund capability is provided by this phase.

A queue-level trigger suppresses held estimate accounting intents from all enqueue producers. QuickBooks/Sage consumers and direct bulk export scans also refuse held estimates. Customer portal document/list/project-access/question paths exclude them. Public PDF export rejects before rendering/uploading. No customer send, acceptance, project total update, invoice or provider write is an allowed draft-save effect. Existing ordinary document behavior is preserved.

The effect policy conservatively fingerprints all public/private stored function definitions and application triggers, including transitive PL/pgSQL helpers whose dependencies PostgreSQL does not record. A database function/trigger change invalidates preparation/commit until the exact new effect graph is reviewed and installed. This intentionally broad safety fence means unrelated database-function releases can pause this dormant vertical. Code-only changes are covered by deployment review, not the SQL fingerprint.

Contention uses a company advisory lock plus NOWAIT source/authority table locks; current implementation can return busy on unrelated concurrent table writes. It never waits indefinitely or applies partial changes. Transactions require READ COMMITTED. Durable inspect/prepare counters bound each actor/grant to 6 and company to 30 calls per 60 seconds. Migration DDL itself uses a three-second lock timeout and 120-second statement timeout.
